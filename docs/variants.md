# RTL variants

Status, 2026-09-25: the variant knobs are implemented in `hardcaml/`. The six
named variants below are generated, synthesized and verified: the cocotb suite,
the formal job list and lint all pass on every variant (section 7.2). **None of
them is the submission.** `src/protocol_emulator_core.v` is still the design of record
(`configs/instruction-sram-32.json`), and it is byte-for-byte what the code emits
when no knob is set. The variants exist so that a fallback is ready if routing or
the slow-corner reset timing fails at 8x4, or if the project must fit 6x4
(`docs/area-study.md` sections 4, 5 and 8, `docs/hardening.md` section 7).

The knobs were first prototyped as environment variables in a scratch copy
(`docs/area-study/area-knobs-v2.patch`). Here they are optional fields of the
refinement config, and some semantics differ from the prototype (section 6).

## 1. Using the variants

| Task | Command |
|---|---|
| Generate one variant | `scripts/generate.sh --variant cn` writes `build/variants/cn/protocol_emulator_core.v` |
| Generate any config to any file | `scripts/generate.sh CONFIG.json --output FILE` |
| Generate all named variants and their firmware | `scripts/gen_variants.sh [--publish DIR] [NAME...]` |
| Assemble for a variant | `dune exec bin/assemble.exe -- --firmware uart-rx --variant ../configs/variants/diet4.json --output uart-rx.image.json` |

`build/` is gitignored. Each generated core keeps module name
`protocol_emulator_core` and the usual header,
`// generated by scripts/generate.sh from hardcaml/ + configs/variants/<name>.json -- do not edit`,
so it can replace `src/protocol_emulator_core.v` behind the unchanged
`src/project.v`.

`scripts/gen_variants.sh` stops with an error if any of these checks fails:
1. `configs/instruction-sram-32.json` still regenerates `src/protocol_emulator_core.v`
   byte for byte. The output goes to a temporary file, so `src/` is never
   written.
2. The `base` variant, which has no `options`, equals `src/protocol_emulator_core.v`
   apart from the header line.
3. Every variant whose firmware target matches the design of record (FIFO
   depth 8, barrel shifts) reproduces `firmware/*.json` byte for byte.

With `--publish DIR` it also copies each core to `DIR/<name>.v` and rewrites
`DIR/MANIFEST.sha256`.

## 2. Configuration

A variant is a complete refinement config (`protocol-emulator.refinement.v1`)
with one optional extra field, `"options"`, next to `"architecture"` and
`"implementation"`:

```json
"options": {
  "reset": "async_sync_release",
  "fifo_storage_reset": true,
  "narrow_image_regs": true,
  "debug_counters": false,
  "pc_bits": "saturating_7",
  "shift": "byte_lane"
}
```

- **Absent fields.** Every field is optional. An absent field takes the
  default of the design of record: `"sync"`, `false`, `false`, `true`,
  `"full"`, `"barrel"`. An absent or empty `options` object selects the design
  of record.
- **Rejected input.** Unknown or duplicate fields, wrong JSON types and unknown
  enum strings are rejected (`hardcaml/lib/variant_options.ml`, parsed from
  `refinement_config.ml`).
- **FIFO depth.** `architecture.fifo_words` now accepts 2 and 4 as well as 8
  and 32, both in `Config` and in the assembler's independent `Isa` parser.
  16 is still rejected.

## 3. Knob semantics as implemented

Throughout, "the reset net" (`clear` in `hardcaml/lib/processor.ml`) is the
signal that resets the chip. In every style it keeps gating the same
combinational paths as the design of record:
- the engine's `active` term;
- FIFO accept (`put`/`take`);
- host write-ready and read-valid;
- SRAM `A_MEN` and the program-write enable;
- mover eligibility;
- pin-trigger delivery;
- pin outputs and output enables.

### 3.1 `reset`

| Style | Reset net | How registers use it | Assertion | Release |
|---|---|---|---|---|
| `sync` (default) | `~rst_n \| ~ena` (combinational from the pins) | Synchronous clear to 0 on every register. FIFO count and pointers use net OR FLUSH. | At the next edge | At the next edge |
| `sync_registered` | `~reset_sync_2`, where `reset_sync_1 <= rst_n & ena` and `reset_sync_2 <= reset_sync_1`. Both are plain flops with no reset. | As `sync` | 2 edges later | 2 edges later |
| `async` | `~(rst_n & ena)` (combinational from the pins) | Asynchronous active-high reset to 0 on every register, including the pin synchronizers and FIFO count and pointers. FLUSH stays a synchronous clear of count and pointers and is no longer ORed with the chip reset. | Immediately | Immediately (asynchronous to `clk`) |
| `async_sync_release` | `~reset_sync_2`, where `reset_sync_1` (D = 1) and `reset_sync_2` (D = `reset_sync_1`) are asynchronously reset by `~(rst_n & ena)` | As `async` | Immediately | 2 edges later |

**Edge-exact timing.** Call "low at edge t" the case where `rst_n & ena` is
low when edge t samples it.
- `sync`: registers clear at edge t and stay cleared while the input is low.
  If the input is high at edge m, edge m is the first functional edge.
- `sync_registered`: registers clear at edge t+2. Once the input is high from
  edge m on, the first functional edge is m+2. A single-cycle low pulse still
  produces one full cycle of reset.
- `async`: registers clear as soon as `rst_n` or `ena` falls and leave reset as
  soon as both are high, so edge m is the first functional edge.
- `async_sync_release`: registers clear as soon as `rst_n` or `ena` falls. Once
  the input is high from edge m on, they stay held through edge m+1, and the
  first functional edge is m+2.

**What each style is for.**
- `sync_registered` removes the `rst_n` input-delay paths that fail slow-corner
  setup (`docs/hardening.md` section 7). `rst_n` and `ena` now reach only the D
  input of `reset_sync_1`.
- `async` removes the synchronous-clear logic and, with `fifo_storage_reset`,
  almost every tie cell (3,929 to 8 in `cn`). It does not remove timing from `rst_n`: release becomes a
  recovery/removal check at about 3,800 reset pins.
- `async_sync_release` confines `rst_n` to the two synchronizer reset pins.
  Hardening must still decide how STA treats assertion through their
  reset-to-Q arcs, for example a false path from `rst_n`.

**`Engine.next_pc`.** The instruction SRAM adapter reads this signal. It now
accepts both PC register forms:
- synchronous clear to 0 with no reset, giving `mux2 clear 0 d`;
- asynchronous active-high reset to 0 with no clear, giving `mux2 reset 0 d`,
  the value after an edge at which reset is asserted.

It zero-extends a 7-bit PC to 24 bits. Any other register form is rejected, as
before.

### 3.2 Contract-neutral knobs

**`fifo_storage_reset`.** Each FIFO storage word becomes a register with write
enable `put & (wr == j)`, read through a mux on the read pointer. It replaces
the memory, which has no reset.
- It takes the chip reset only, never FLUSH: an asynchronous reset in the
  asynchronous styles and a synchronous clear from the reset net in the
  synchronous styles.
- Storage is never observable while a queue is empty, so this changes no
  behaviour.
- Only with an asynchronous style does it remove the `tiehi` cells. A
  synchronous-clear flop in CMOS5L still ties `RESET_B`.

**`narrow_image_regs`.** `image_length_k` and `image_loaded_k` become
log2(program_words)+1 = 7 bits instead of 16.
- COMMIT stores `payload[6:0]`. The payload is already required to be at most
  64 and equal to `image_loaded`, which is compared zero-extended.
- The only visible difference is the width of the debug export
  `dbg_image_length`.

### 3.3 ISA-changing knobs (ISA version 3)

**`debug_counters: false`.** Nothing reads the engine's
`completed_instructions` register any more, so it is not emitted. The engine
reports 0, and READ_SELECT 5 reads 0.

**`pc_bits: "saturating_7"`.** The PC register is 7 bits. The option is
rejected for program images larger than 64 words: 127 must lie outside every
image, and the image length must fit the 7-bit comparison.
- **Branch targets.** A JMP or LOOP target (imm24) or JZ target (imm16) with any
  bit above bit 6 set, which means a target of 128 or more, loads 127. Smaller
  targets load unchanged.
- **Sequential PC.** PC+1 cannot wrap, because an instruction issues only while
  PC is below the image length (at most 64).
- **Faults.** Out-of-image PCs still fault with code 2.
- **READ_SELECT 3** reads the 7-bit PC zero-extended. After a branch to a
  target of 128 or more it reads 127 instead of the target.

**`shift: "byte_lane"`.**
- **Valid forms.** SHL and SHR are valid only for `a < 4`, `b = 0`,
  `c < datapath width` and `c & 0xE7 = 0`. So the counts are 0, 8, 16 and 24,
  or only 0 and 8 on a 16-bit datapath.
- **Other counts** are invalid operands and fault with code 1, like any other
  invalid operand.
- **Hardware.** The result is a byte-lane multiplexer on `c[4:3]` instead of a
  barrel shifter.

**ISA version.** READ_SELECT 7 reads 3 when `debug_counters` is false,
`pc_bits` is `saturating_7` or `shift` is `byte_lane`. Otherwise it reads 2.

### 3.4 Assembler and firmware

The assembler gains three ways to target a variant:
- `Isa.encode ~byte_lane_shifts` and `Assembler.assemble_with ~byte_lane_shifts`
  reject SHL/SHR counts that are not a byte lane.
- `bin/assemble.exe --byte-lane-shifts` does the same from the command line.
- `bin/assemble.exe --variant CONFIG` reads the variant's architecture (for
  built-ins) and its shift restriction. It rejects a `--source` whose
  architecture differs from the variant's.

Assembled images keep schema `protocol-emulator.firmware-image.v1` and
`isa_version: 2`. An image that passes the byte-lane check is also a valid ISA
v2 image, and `test/harness.py` accepts only ISA 1 or 2 images.

`Firmware.make ~byte_lane_shifts` changes the built-in examples as follows:
- **Fused-issue built-ins** already use only `SHL/SHR c = datapath - 8` and are
  unchanged.
- **Scalar SPI controller.** Its MSB mask is built as `LOAD y,0x80; SHL y,width-8`
  and its 1-bit shift becomes `ADD tx,tx`. The program length and timing are
  unchanged.
- **Scalar JTAG** needs a 1-bit SHR and is rejected.

`scripts/gen_variants.sh` writes the 19 committed images for each variant to
`build/variants/<name>/firmware/`:
- For `base`, `rstreg`, `cn` and `cn_s2` they are byte-identical to `firmware/`.
- For `diet4` and `diet2` every instruction word and `bytecode_sha256` is
  unchanged. The architecture binds `fifo_words` 4 or 2, so the source and
  image hashes differ.
- `flagship-scenario.json` is not regenerated. It prefills 8 TX words into
  engine 0, which exceeds a 4- or 2-deep queue.

## 4. Named variants and contract changes

All six use the SRAM-32 architecture: 4 engines, 32-bit, 64 words, fused issue
and no prefetch. The configs are in `configs/variants/`.

| Variant | FIFO | Options | ISA | Contract changes |
|---|---:|---|---:|---|
| `base` | 8 | none | 2 | None; equals the design of record. |
| `rstreg` | 8 | `reset: sync_registered` | 2 | Reset and deselection take effect 2 edges later, and release is 2 edges later: write-ready appears in the third cycle after `rst_n` rises, not the first. Until two edges have sampled `rst_n`, a 4-state simulation shows X. The Python model and the cocotb reset expectations need the 2-cycle delay. |
| `cn` | 8 | `reset: async`, `fifo_storage_reset`, `narrow_image_regs` | 2 | Register state after every edge equals the design of record's when `rst_n`/`ena` change between edges. Outputs not masked combinationally in the design of record (`uo_out` fault, IRQ and read nibble) clear as soon as `rst_n` or `ena` falls instead of at the next edge. Release is asynchronous to `clk`. |
| `cn_s2` | 8 | as `cn`, `reset: async_sync_release` | 2 | Assertion as `cn`; release 2 edges later, as `rstreg`. |
| `diet4` | 4 | as `cn_s2`, `debug_counters: false`, `pc_bits: saturating_7`, `shift: byte_lane` | 3 | Everything in `cn_s2`, plus the ISA changes and a queue depth of 4, listed below. |
| `diet2` | 2 | as `diet4` | 3 | As `diet4` with 2-deep queues. |

The `diet` variants change the following:
- **Queue depth.** FIFO depth 4 (or 2) is a machine parameter that `docs/isa.md`
  currently limits to 8 or 32.
- **READ_SELECT 5** reads 0.
- **READ_SELECT 3** reads 127 after a branch to 128 or more.
- **Shifts.** SHL/SHR accept only byte-lane counts; other counts fault with
  code 1, and the assembler rejects them.
- **READ_SELECT 7** reads 3.
- **Strict overflow.** Its rule about preserving the completed count
  (`isa.md`) has nothing left to preserve.
- **Firmware.** Every committed image still assembles, because all 15 shifting
  images shift by 24. The flagship scenario needs a TX top-up instead of an
  8-word prefill.

**Flows.** Areas come from `docs/area-study/scripts/synth3.sh`, unchanged:
- `ll66` is the LibreLane 3.1.0.dev3 "AREA 0" replica, run with the Yosys 0.66
  inside the LibreLane SIF;
- `plain` is the study's revision-1 flow;
- all runs use the typical-corner liberty and treat the SRAM macros as black
  boxes.

**Scope and model.**
- **Core** is `protocol_emulator_core` alone, the scope of `docs/area-study.md`.
- **Wrapper** adds `src/project.v`, which is what the TT flow synthesizes.
- **U and D** use the study's model (section 2.4):

  ranked, because synthesis noise is that large. `rstreg`'s +2.6K in the core

  not a placed result.

## 6. Differences from the area-study prototype (`area-knobs-v2.patch`)

| Item | Prototype | Implemented |
|---|---|---|
| Knob source | Environment variables | `options` object in the refinement config; the default path emits the design of record byte for byte |
| Register names | Every register renamed (e.g. `e0_pc`) | Unchanged; only `reset_sync_1`/`reset_sync_2` are named |
| PC saturation | Targets ≥ 64 saturate to 127 (`select v 23 6`) | Targets ≥ 128 saturate to 127 (spec). Targets 64–127 keep their value; both forms fault with code 2 |
| Byte-lane shifts | `c & 0x18` used as the count; every count below the width stays valid | Only 0/8/16/24 are valid; any other count faults with code 1 (spec). The assembler rejects them |
| Counters off | Completed counter replaced by a 1-bit wire | Counter register left without a reader (not emitted); same netlist effect |
| Release synchronizer | `AREA_RST_SYNC=2`; Diet Ei/Gi were measured without it | `async_sync_release`, used by `cn_s2`, `diet4` and `diet2` (spec) |
| Synchronous reset registered | Not prototyped | `sync_registered` (new) |
| `Engine.next_pc` with asynchronous reset | Returned `d` and ignored the reset | Returns the reset value while the asynchronous reset is asserted |
| FIFO storage registers under synchronous reset | `AREA_FIFO_REGS` storage without reset (ties) | `fifo_storage_reset` storage takes the synchronous chip clear (spec: "take the reset") |
| FIFO depths | 2/4/8/16/32 | 2/4/8/32 (spec) |
| Not implemented | `AREA_DP_NOCLEAR`, `AREA_NO_ENA`, `AREA_NO_STATUS`, `AREA_NO_MOVER`, `AREA_NO_SHIFT`, `AREA_RX_DEPTH`, `AREA_COMPLETED_WIDTH=16`, `area_blocks.exe` | Measurement-only or rejected items |

**How the lockstep works.** `variant_test.ml` runs each variant in Cyclesim next
to the design of record with the same architecture. It compares every output,
including the debug exports, before and after every edge.
- **Reset styles** are compared through their timing transformation. The
  reference sees `rst_n` as follows:
  - for `sync_registered`, `(rst_n & ena)` delayed 2 edges;
  - for `async`, `(rst_n & ena)`;
  - for `async_sync_release`, the AND of `(rst_n & ena)` over the last 3 edges.
- **Asynchronous resets** are emulated exactly: all registers reset at
  assertion and at every held edge, and the two synchronizers keep clocking
  during release.
- **Skipped comparisons.** The before-edge comparison in the cycle where an
  asynchronous reset is first asserted is skipped, because that difference is
  intended. So is the after-edge comparison at an edge where the reference's
  reset input changes. The following comparison still checks both.
- **Unobservable storage.** FIFO storage is masked where it is not observable:
  invalid heads, words not pushed, and cycles with no mover grant.
- **ISA-changing variants** get traffic that avoids READ_SELECT 3/5/7 and
  non-lane shifts. It still includes out-of-range branches, which fault with
  code 2 in both designs.

The checks above ran while the knobs were written. The cocotb suite with the
variant model (`test/model/variant.py`, `PE_VARIANT`), the formal job list with
`formal/run.sh --variant` and an integration rerun of everything on the final
source came later; section 7.2 has their results. The formal generators read
`Refinement_config.options` and the `reset_sync_1` and `reset_sync_2` register
names, so those must stay stable.

STA and hardening have not been run on any variant.
