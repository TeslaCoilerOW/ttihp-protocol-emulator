# 6x4 fallback build (`diet4`)

Last updated 2026-09-26. This page describes the 6x4 build of the `diet4`
variant: how it differs from the 8x4 design of record, how its floorplan
avoids the precheck Pin-check failure, the local sign-off evidence, the CI
workflow that builds it, and how to make it the submission.

**Status.**

- The design of record is unchanged: 8x4, `src/` and `info.yaml` at
  `c118027` (tag `v0.1-hardened`). Its official gds, precheck and gl_test
  passed in GitHub run 36144357821.
- The competition page
  (<https://blog.janestreet.com/protocol-emulator-asic-competition/>, read
  2026-09-25) says: "The current maximum area is 6x4 tiles per design. We are
  working on the possibility of scaling up to 8x4 tiles (~30% more area)."
  The 6x4 build keeps a candidate that fits the stated maximum.
- The 6x4 build is defined by `variants6x4/` and built by
  `.github/workflows/gds_6x4.yaml`. Nothing in it changes the 8x4 flow.
- Every result on this page is local (MIT Engaging cluster, the gds action's
  LibreLane 3.1.0.dev3 image and IHP PDK revision `2bbec755`), with Slurm job
  ids. The GitHub workflow had not run when this page was written.

**Summary of the evidence (local).**

- With the current `src/config.json` keys (halo 16.48), every "tworow" 6x4
  floorplan still gets one short VPWR/VGND strap pair, at the right core edge
  beside the top row, which the precheck Pin check rejects (section 2, job
  23974838). Two fixes remove it: a halo of 26.96 µm (derived from the gap
  geometry) or one `FP_OBSTRUCTIONS` box over that gap.
- Eleven full-flow runs of `diet4` at 6x4 with the action's settings
  (`OPENROAD_THREADS` 4, 20 ns): ten of them pass route DRC 0, antenna 0, LVS 0,
  typ setup and all-corner hold, the unmodified TT precheck 9/9 (0 KLayout DRC
  items in 332 rule categories) and the gate-level cocotb suite (36 pass,
  30 skipped by design, 0 fail, the counts of the official 8x4 gl_test).
- Selected (`variants6x4/config.overlay.json`, section 4):
  `fp6_tworow_trk_top30_edgeobs` at density 60. Utilization 56.3%
  (standard cells 49.5%); setup WS typ +4.29 ns, fast +8.50 ns, slow −2.80 ns
  (not a sign-off corner); hold WS min +0.099 ns; run 23980402_9, precheck
  23988194, gate level 23987753. A repeat on another node (23988535_1) gave
  identical metrics and netlists, and a GDS that differs only in its
  timestamps.
- The committed core regenerates byte for byte from `hardcaml/` +
  `configs/variants/diet4.json` at `c118027` and at `aa07868`. On the switched
  workspace the RTL suite passes 66/66 at `c118027` (job 23975151) and
  102/102 with the larger suite of `aa07868` (job 23990752); the gate-level
  suite of `aa07868` passes on the selected netlist with 46 pass, 56 skipped,
  0 fail (job 23990753).


## 1. What differs from the 8x4 design of record

### 1.1 Core: `diet4`, ISA version 3

The 6x4 core is the `diet4` variant (`configs/variants/diet4.json`), generated
by the same Hardcaml sources as the design of record. It keeps module name
`protocol_emulator_core`, the eight `RM_IHPSG13_1P_64x16_c2` instances and
their flattened names, so it sits behind the unchanged `src/project.v`. The
committed copy is `variants6x4/protocol_emulator_core.v` (sha256
`cc27c465…`, provenance in `variants6x4/PROVENANCE.json`).

| | 8x4 design of record | 6x4 `diet4` |
|---|---|---|
| Config | `configs/instruction-sram-32.json` | `configs/variants/diet4.json` |
| Core sha256 | `26a873db…` | `cc27c465…` |
| Engines, datapath, program words | 4, 32-bit, 64 per engine | same |
| Queue depth (`fifo_words`) | 8 | 4 |
| Reset (`reset`) | `sync`: synchronous clear from `rst_n`/`ena` | `async_sync_release`: asynchronous assertion, release two clock edges after `rst_n` and `ena` are both high |
| Completed-instruction counters (`debug_counters`) | yes; READ_SELECT 5 reads the count | removed; READ_SELECT 5 reads 0 |
| PC (`pc_bits`) | full | 7-bit, saturating: a JMP/LOOP/JZ target of 128 or more loads 127 (then faults with code 2, as before); READ_SELECT 3 reads 127 |
| Shifts (`shift`) | barrel | byte lane: SHL/SHR counts 0, 8, 16, 24 only; any other count faults with code 1, and the assembler rejects it |
| Contract-neutral knobs | none | `fifo_storage_reset`, `narrow_image_regs` |
| ISA version (READ_SELECT 7) | 2 | 3 |
| TT synthesis area, with `src/project.v` (docs/variants.md §5) | 462,710 µm² | 298,478 µm² |

The contract changes are specified in `docs/isa.md` ("Variants") and
`docs/variants.md` sections 3 and 4. For a host or firmware author:

- **Firmware.** Every image in `firmware/` still assembles and runs: all
  shifting images shift by 24, and the largest branch target is 54. The
  flagship scenario prefills 8 TX words, more than a 4-deep queue; the
  top-up version `firmware/flagship-scenario-topup.json` is the one to use.
- **Reset.** Write-ready appears in the third cycle after `rst_n` rises
  instead of the first. Outputs that the design of record masks only at the
  next edge (fault, IRQ, read nibble) clear as soon as `rst_n` or `ena` falls.
- **Datasheet.** `docs/info.md` describes the design of record (ISA version 2,
  8-word queues). A switch to 6x4 must update it (section 6).

Verification of `diet4` so far (all local): the cocotb suite, 16 extra random
seeds (4,096 cases, 15.49M cycles), formal 16/16 with both negative controls
failing, and the gate-level subset on a LibreLane-replica netlist
(`docs/variants.md` section 7.2, jobs 23758015, 23758041, 23761207), plus the
runs in section 3 below.

## 2. Short power straps at 6x4: derived halo or floorplan obstruction

The official precheck of `73536f0` failed its Pin check because pdngen adds a
short VPWR/VGND Metal4 strap pair over any standard-cell rows that no
full-height lattice stripe crosses, and Magic.WriteLEF exports those straps as
power ports that do not reach both block edges (`docs/drc-triage.md`
section 6). At 8x4 the only such rows were in the 32.96 µm gaps between paired
macros, and `FP_MACRO_HORIZONTAL_HALO` 16.48 (half the gap) removed them.

At 6x4 that halo is not enough. `variants6x4/row_islands.py` models
`OpenROAD.CutRows` (macro box plus halo, cut ends snapped to the 0.48 µm site
grid) and the stripe lattice, and lists every row segment that no VPWR and no
VGND stripe crosses. For every "tworow" 6x4 floorplan, the gaps are:

| Gap | Width | Stripe pair inside | Halo that removes its rows |
|---|---:|---|---:|
| between neighbouring macros of a row (k differs by 4) | 32.96 µm | no | ≥ 16.48 µm (half) |
| core left edge to the bottom row's first macro (k 0) | 8.16 µm | no | < default 10 µm, already empty |
| top row's last macro (k 15, ends x 1259.44) to the core right edge (1286.40) | **26.96 µm** | **no** (next pair at x 1309.64 is outside the core) | **≥ 26.96 µm** (whole gap) |
| bottom row's last macro (k 12) to the core right edge | 229.28 µm | yes | none |

So the smallest halo that closes every stripe-free gap is **26.96 µm**. The
model's sweep on a 0.01 µm grid finds the first island-free halo at 26.49 µm
(the remainder drops below one site); the floorplans use the geometric value.
`fp6_block_trk` needs only 16.48; `fp6_spread_trk` and `fp6_columns_trk` also
need 26.96 (`row_islands.py --floorplan floorplans --derive`).

There are two ways to remove the right-edge rows, and both were built:

- **(a) Derived halo.** `FP_MACRO_HORIZONTAL_HALO` 26.96. The files
  `floorplans/<id>_h26p96.json` are the three tworow floorplans with this
  value in their `config` block, written by
  `row_islands.py --derive --emit floorplans`.
  `macros/check_macro_floorplan.py` rejects this value: it requires macros to
  be at least two halos apart, and 32.96 < 2 × 26.96. LibreLane has no such
  rule; overlapping halos only merge the cut regions (the 8x4 halo-17 build
  passed the flow and the precheck, `docs/drc-triage.md` section 6), and all
  runs below with (a) have overlapping halos. Their sweep snapshots record the
  checker output without enforcing it.
- **(b) Floorplan obstruction.** Keep `src/config.json`'s 16.48 (half the
  pair gap) and add one `FP_OBSTRUCTIONS` box over the right-edge gap: x from
  the top row's last macro edge (1259.44) to the core edge (1286.40), y from
  that row's y minus the 10 µm vertical halo to the core top (706.86). In
  LibreLane 3.1.0.dev3 the box becomes a hard placement blockage before the
  rows are made, and OpenROAD makes no row under it. The files are
  `floorplans/<id>_edgeobs.json`. The committed checker accepts them, and
  `row_islands.py` models the box as a blockage without halo.

**Model check against LibreLane.** The model reproduces every strap of the
earlier runs: 4 channels for 8x4 with the 10 µm default (run2, the row segments
x 393.12..405.60, y 3.78..79.38 of `docs/drc-triage.md`), 0 with 16.48 and 17,

## 4. Selected configuration

`variants6x4/config.overlay.json` is **`fp6_tworow_trk_top30_edgeobs` at
density 60**, option (b) of section 2.

- **Why this point.** Among the ten passing runs it has the largest typ
  setup slack (+4.29 ns) and the least negative slow-corner slack (−2.80 ns);
  global-routing overflow is 6 and detailed routing is clean after 7
  iterations. The best run with the derived halo (a),
  `fp6_tworow_trk_top30_h26p96` at density 55, is within 0.04 ns at typ
  (+4.26 ns, slow −3.16 ns) and passes everything as well; it is the fallback
  if the obstruction key is not wanted.
- **Other reasons for (b):** it keeps `FP_MACRO_HORIZONTAL_HALO` and
  `PL_TARGET_DENSITY_PCT` at the values of `src/config.json`, and the
  committed floorplan checker accepts it.
- **What the overlay sets.** `MACROS` instances (bottom FS row k 0/4/8/12 at y
  3.87, top N row k 3/7/11/15 at y 612.36), `FP_OBSTRUCTIONS`
  `[[1259.44, 602.36, 1286.40, 706.86]]`, and `PL_TARGET_DENSITY_PCT` 60 and
  `FP_MACRO_HORIZONTAL_HALO` 16.48 restated, so a later change of those keys in
  `src/config.json` does not change the 6x4 build without a new sign-off.
- **Same configuration as the signed-off run.** `switch.py apply` on a copy of
  the committed tree produces a `src/config.json` whose keys and values equal
  the snapshot of run 23980402_9, a core that is byte-identical, and an
  `info.yaml` that differs only in the comment on the `tiles` line. The
  committed `floorplans/fp6_tworow_trk_top30_edgeobs.json` gives the same
  snapshot hash as the tested one (only its description text differs).
- **Reproducibility.** Both finalists were run a second time on another node
  with the same snapshot (array 23988535): `fp6_tworow_trk_top30_edgeobs` d60
  (23988535_1) and `fp6_tworow_trk_top30_h26p96` d55 (23988535_0). Every
  metric (utilization, instance count, wirelength, hold buffers, the
  detailed-routing history, setup and hold slack at all corners) is identical
  to the first run, and so are the final `nl`, `pnl` and LEF files. The
  repeat of the selected point also passed the precheck 9/9 (23989729) and the
  gate-level suite (23989730); its GDS equals the first one after masking the
  BGNLIB/BGNSTR timestamp records. The earlier 8x4 evidence
  (`docs/sweep.md`, repeatability; the local halo-16.48 build and run
  36144357821 both at typ +0.89 ns) points the same way: the action with the
  same settings is expected to reproduce these numbers. That remains to be
  confirmed by the first `gds_6x4` run.

## 5. CI: `.github/workflows/gds_6x4.yaml`

Triggers: push to `main` and `workflow_dispatch`. Concurrency group
`gds-6x4-<ref>` with `cancel-in-progress`, so a newer push cancels a run that
is still going. The 8x4 `gds.yaml` is unchanged and keeps running on every
push.

| Job | What it does | Fails when |
|---|---|---|
| `core_current` | Sets up the pinned OCaml toolchain (as `regen.yaml`), runs `variants6x4/check_core.sh` (regenerates `diet4` into a temporary file and compares), then `variants6x4/switch.py check` | the committed 6x4 core differs from `hardcaml/` + `configs/variants/diet4.json`; the overlay no longer matches `src/config.json` (unknown key, different MACROS instance names, core hash not in `PROVENANCE.json`); the merged placement would get a short power strap |
| `rtl_test` | Switches the workspace, then runs the cocotb suite with `PE_VARIANT=diet4` and `PE_CORE=../src/protocol_emulator_core.v` (Icarus 13.0 as in `test.yaml`) | any test fails |
| `gds` | Checks out, runs `variants6x4/switch.py apply`, then `TinyTapeout/tt-gds-action@ihp-cmos5l` with `librelane-version: 3.1.0.dev3`, exactly as `gds.yaml` | the flow fails |
| `precheck` | `TinyTapeout/tt-gds-action/precheck@ihp-cmos5l` on this run's `tt_submission` artifact | any precheck check fails |
| `gl_test` | Checks out and switches, then `TinyTapeout/tt-gds-action/gl_test@ihp-cmos5l` with `PE_VARIANT=diet4` in the job environment | any gate-level test fails |

How the switch reaches the actions:

- `tt_tool.py --create-user-config` reads `info.yaml` and `src/config.json`
  after the switch step, so the flow sees 6x4 tiles, the 6x4 DEF template,
  the 6x4 placement and obstruction, and the `diet4` core.
- The `tt_submission` artifact carries the switched `src/` and `info.yaml`.
  The precheck reads `tiles` from that `info.yaml`.
- `gl_test` downloads the artifact over the checkout, copies the gate-level
  netlist to `test/gate_level_netlist.v` and runs `GATES=yes make`. In GL mode
  `test/Makefile` compiles only the netlist, the PDK cell models and the SRAM
  models, so the core source is not used; `PE_VARIANT=diet4` makes
  `test/variants.py` load the `diet4` reference model
  (`configs/variants/diet4.json`, cross-checked against its `SPEC`).
- Artifacts belong to the workflow run, so this workflow's `tt_submission`
  never mixes with `gds.yaml`'s.

The `viewer` job of `gds.yaml` is not repeated here.

## 6. Switching the submission to 6x4

Do this only if 8x4 is not confirmed for the competition. On a clean checkout
of `main`:

1. `python3 variants6x4/switch.py apply`, then commit the three files it
   rewrites (`src/protocol_emulator_core.v`, `src/config.json`, `info.yaml`).
   `src/config.json` is rewritten by `json.dump`, so its comment keys collapse
   to one; restoring the comments by hand is optional (tt-support-tools reads
   the file with `json.load`).
2. Make the other workflows test the new core:
   - `regen.yaml`: regenerate from `configs/variants/diet4.json` instead of
     `configs/instruction-sram-32.json` (and the `Makefile` `CONFIG` default,
     and `scripts/generate.sh`'s default config, or pass the config
     explicitly). Until then `regen` fails, because `src/` no longer matches
     the design-of-record config.
   - `test.yaml`: set `PE_VARIANT: diet4` for the `test` job. The default
     (`base`) model does not match the `diet4` core.
   - `gds.yaml`: set `PE_VARIANT: diet4` for the `gl_test` job.
   - `formal.yaml`: run `formal/run.sh` with `--variant diet4`
     (or `FORMAL_VARIANT=diet4`); without it the proofs cover the
     design-of-record RTL, not the submitted core.
3. Update the documents that describe the design of record: `docs/info.md`
   (ISA version 3 on READ_SELECT 7, READ_SELECT 5 reads 0, 4-word queues,
   byte-lane shifts, saturating PC, reset release timing, 6x4 tiles, and the
   top-up flagship scenario in the demo), `README.md` (8x4 statements) and
   `docs/isa.md` if the variant section should become the main contract.
4. Remove `gds_6x4.yaml` in the same commit: after the switch its
   `switch.py apply` step refuses the already switched checkout, and
   `gds.yaml` now builds the 6x4 design. Push and require green `gds`,
   `precheck` and `gl_test` on the switched commit.

To return to 8x4, revert that commit.

## 7. Limits and open items

- **Local, not official.** No GitHub run of `gds_6x4.yaml` existed when this
  page was written. The sign-off runs use the action's LibreLane image,
  `OPENROAD_THREADS` 4 and 4 CPUs, but apptainer instead of docker, and the
  precheck ran with KLayout 0.30.9 instead of the action's 0.30.4
  (`docs/drc-triage.md` section 5: both versions report 0 items on the 8x4
  run2 GDS).
- **Slow corner.** Setup at the slow corner (1.08 V, 125 °C) is reported and
  not signed off, as for 8x4 (`docs/hardening.md` section 7).
- **Reset timing.** `diet4` uses asynchronous assertion with a two-flop
  release synchronizer. Recovery/removal checks on the asynchronous reset
  pins and the treatment of `rst_n` through the synchronizer's reset arcs have
  not been reviewed separately (`docs/variants.md` section 3.1); formal
  models the asynchronous reset as synchronous.
- **Floorplan checker.** `macros/check_macro_floorplan.py` rejects the
  derived-halo floorplans `*_h26p96` (two-halo rule, section 2). The selected
  obstruction floorplan passes it. Using option (a) as the submission would
  need that rule relaxed to allow overlapping halos.
- **Datasheet and host.** `docs/info.md` and the demo scripts describe the
  design of record; section 6 lists what changes.
