# Instruction-level specification

[verification.md](verification.md) section 5 names a common-mode risk: the
RTL (`hardcaml/lib`) and the lockstep reference model
(`test/model/reference.py`) come from the same specification and the same
development process, so matching cycles show that the two agree, not that
either implements the ISA. `formal/isa/` adds an instruction-level
specification in the style of riscv-formal's per-instruction checks. It was
written from [isa.md](isa.md) only and is proved against the production RTL
with SymbiYosys. This page records what it specifies, how it is checked, what
it does not cover, and the disagreements it found.

**Revision.** Every result below is for the committed tree at `16cfc20`,
exported with `git archive`, plus the files of `formal/isa/` and the
registration in `formal/run.sh`. The RTL was generated by
`formal/run.sh --generate-only` from that tree. Configuration:
`configs/instruction-sram-32.json` (4 engines, 32-bit datapath, 64-word
images in the IHP `RM_IHPSG13_1P_64x16_c2` FUNCTIONAL models, 8-word FIFOs,
fused issue). Tools: OSS CAD Suite 2026-07-29 (Yosys 0.67, SymbiYosys,
yices through smtbmc). At `f246775` (after the Hardcaml refactor `dd7dae3`)
the generated RTL and all 49 mutants are byte-identical to those of
`16cfc20`, and an independent re-run of the five CI groups and of the
bounded jobs `isa_queue_rx`, `isa_xfer_e2e` and `isa_queue_tx` with their
covers and negative controls met every expectation (Slurm jobs
24420171 to 24420184).

## 1. Independence

The specification modules (`isa_insn.sv`, `isa_insn.vh`, `isa_cmd.sv`) and the
harness (`isa_spec.sv`) were written from [isa.md](isa.md), with port names
and harness conventions taken from `formal/` (the observation ports of
`processor_fv.v`, `formal/README.md`, the existing harnesses). `hardcaml/lib`,
`test/model` and the logic of the generated RTL were not read while the
specification was written. A read log with times was kept outside the
repository. The specification was frozen before the generated RTL was read to
place the seeded defects of the negative controls (section 5), and before the
reference model was read for section 7. After the freeze the four files
changed in comments (the `target of:` names of the negative controls and
header text), by the removal of one cover branch identical to the branch
after it, and by one added property: the two-flip-flop input synchronizer in
`isa_pinmap` ("Inputs pass through two flip flops"). `gen_sby.py` gained the
mutant of each negative control.

Where [isa.md](isa.md) does not decide a behaviour, the first version of the
specification took a literal reading. Each such reading that the RTL did not
satisfy is listed in section 6; for those, the specification now follows the
RTL and marks the point in a comment.

One abstraction comes from `formal/engine_safety.sv` rather than from
[isa.md](isa.md): the LIMIT register reads 0 for the reset default 65535.

The independence is from `hardcaml/lib`, `test/model` and the logic of the
generated RTL, not from every earlier statement of the semantics. Before the
specification was written, `formal/engine_safety.sv` (in full) and
`formal/processor_inductive.sv` were read for the port conventions. Both are
earlier, RTL-derived formal harnesses that also state instruction and command
behaviour: `engine_safety.sv` asserts NOP, WAIT, JMP, LOOP, JZ, blocked
PULL/PUSH, the strict PUSH overflow, START (PC 0, completed count 0) and the
WAITPIN/WAITEVENT timeout in the form `blocked_cycles + 1 >= effective_limit`,
the same form as `isa_insn_waitpin` and `isa_insn_waitevent`;
`processor_inductive.sv` asserts TRIGGER and the ownership and queue-level
invariants that also appear in V (section 3.2). The specification did not
simply copy them: its first reading of START kept the completed count, which
`engine_safety.sv` states is cleared (D2 in section 6).

## 2. What is specified

### 2.1 Architectural state and its observation

The specification works on the architectural state of one engine and its
environment. `isa_spec.sv` reads it from the observation ports of
`processor_fv.v` (`formal/gen/generate_fv.ml`: plain outputs of existing
registers):

| Architectural state ([isa.md](isa.md)) | Observation |
|---|---|
| PC, running, fault code | `fv_pc`, `fv_running`, `fv_fault_code` |
| registers tx, rx, x, y | `fv_tx`, `fv_rx`, `fv_x`, `fv_y` |
| COUNT/LOOP repeat counter | `fv_repeat_count` |
| remaining WAIT hold | `fv_wait_timer` |
| LIMIT (reset default 65535) | `fv_wait_limit`, where 0 means 65535 |
| consecutive unsuccessful WAITPIN/WAITEVENT samples | `fv_blocked_cycles` |
| logical pin values (SET, OUT), logical output enables (DIR) | `fv_logical_output`, `fv_logical_enable` |
| PINS clock/TX/RX pin fields | `fv_transfer_pins` |
| completed-instruction count (READ_SELECT 5) | `fv_completed_instructions` |
| XFER in progress | `fv_transfer_edges != 0` |
| committed image and its length; loading | `dbg_image_valid`, `dbg_image_length`, `fv_image_writing`, `fv_image_loaded` |
| ownership, open-drain mask | `dbg_ownership`, `dbg_open_drain` |
| TX/RX queue levels, RX head, queue handshakes | `dbg_tx_level`, `dbg_rx_level`, `dbg_rx_head`, `dbg_tx_pop`, `dbg_tx_push`/`dbg_tx_data`, `dbg_rx_push`/`dbg_rx_data`, `dbg_rx_pop` |
| event mailboxes, deliveries, consumption | `dbg_events`, `dbg_event_set`, `dbg_event_clear` |
| synchronized pin inputs (second stage) | `dbg_synced_pins` |
| common timestamp | `fv_timestamp` |
| accepted host command | `dbg_command_accepted`, `dbg_command_code`, `dbg_command_payload`, `dbg_host_selected` |
| pins, IRQ, fault output | `uio_out`, `uio_oe`, `uo_out[7:6]` |

### 2.2 Instructions

An *issue edge* of engine `k` at address `A` is a rising edge before which
engine `k` runs without a fault, no WAIT hold and no XFER is in progress,
`PC = A` lies inside the committed image, and the edge carries no reset or
deselection, START or STOP of engine `k`. For every opcode, a module of
`isa_insn.sv` states the architectural state after an issue edge as a function
of the state before it and the image word `W` at `A`:

- the next PC, the running state and the fault code;
- the four registers, the repeat counter, the WAIT hold, LIMIT and the blocked
  count;
- the logical outputs and enables, the PINS configuration and the
  completed-instruction count;
- the queue effects: a TX pop, an RX push and the pushed word;
- the mailbox effects: consumption, and the mailboxes SIGNAL makes pending;
- whether an XFER is in progress after the edge.

Common rules come from [isa.md](isa.md), "Machine" and "Instructions".
"Unused operands are zero": a non-zero unused operand is an invalid operand.
Pins are 0..7, and a pin write or output enable outside ownership faults.
"A nonblocking instruction costs one cycle". A faulting instruction does not
complete: PC, the count, the registers and the queues keep their values, and
the logical output and enable registers are left unspecified, because "release
output enables" is a pin-level fact (`isa_pinmap`). Opcodes 30 to 255 fault
with code 1. A PC outside the committed image faults with code 2 before any
word is decoded (`isa_fetch`).

### 2.3 Other properties

| Check | Specified behaviour ([isa.md](isa.md)) |
|---|---|
| `isa_fetch` | An engine ready to issue with PC outside the committed image faults with code 2; nothing else changes and no queue word moves. |
| `isa_hold` | During a WAIT hold each edge only counts the hold down. During an XFER no FIFO operation or event consumption occurs, PC and count stay until the final edge and then advance by one, and x, y, the repeat counter, LIMIT, the enables and PINS do not change. |
| `isa_idle` | A halted or faulted engine changes no execution state and moves no queue word or event, except through START, CLEAR-FAULT or reset (a STOP or BEGIN may release its logical enables). `dbg_start` occurs exactly for an accepted START of the engine, `dbg_stop` only for STOP, BEGIN or reset. |
| `isa_pinmap` | On every cycle: each pin is driven only by its owner, masked by run and fault; an open-drain pin outputs 0 and is enabled when its logical enable is set and its logical value is 0; during reset or deselection no pin is enabled and the host write-ready and read-valid outputs are low; `uo6` (IRQ) is set exactly when a mailbox is pending or an RX queue is non-empty; `uo7` is set when an engine has a fault; outside reset the first input stage takes `uio_in` and the second, which the engines sample, takes the first. |
| `isa_inv` | The invariant V of section 3.2. |
| `isa_reset` | From any state, one reset edge stops every engine, clears faults, images, queues, mailboxes, ownership, open-drain, triggers and routes, restores LIMIT to 65535, releases every pin and lands in V. |
| `isa_queue_tx` | "tx := TX FIFO head": the word a PULL loads is the oldest word pushed into the engine's TX queue by the host or the mover and not yet pulled. |
| `isa_queue_rx` | "append rx to RX FIFO": the word PUSH appends becomes the RX head once the words ahead of it are gone. |
| `isa_xfer_e2e`, `_a4`, `_b5` | The whole XFER: the clock pin starts at CPOL and toggles on each of the `2a` transitions, `b` cycles apart; with drive the TX pin carries the data bits in order (CPHA0: first bit on issue, next bits on idle edges; CPHA1: bits on active edges); with sample rx shifts in the synchronized RX pin on active (CPHA0) or idle (CPHA1) edges, left for MSB-first and right for LSB-first; no queue operation occurs; PC and the count advance on the final idle edge; nothing else changes. |

### 2.4 Host commands

`isa_cmd.sv` has one property module per window-0 command that changes engine
or queue state. On the edge that accepts a command (`dbg_command_accepted`) it
asserts that the command was legal, and on the next cycle the state of each
affected engine:

| Command | Legal when accepted | State after the command |
|---|---|---|
| SELECT | | the selected engine is the payload's low two bits |
| BEGIN | | the engine is stopped, its image invalid, loading open at address 0 |
| COMMIT | loading is open, `1 <= length <= 64`, at least `length` words loaded | image valid with that length, loading closed |
| OWN | engine halted, no overlap with other engines' pins, open-drain inside ownership | ownership and open-drain mask as given; other engines' unchanged |
| START | every engine in the mask committed and fault-free; no queue flush, pop, push or event consumption on the edge | running at PC 0; registers, repeat counter, hold, blocked count, XFER state, logical outputs and enables, PINS and the count cleared; LIMIT 65535; image, ownership and open-drain unchanged; mailbox kept |
| STOP | no pop, push or consumption on the edge | halted; PC, registers, counters, fault, hold and blocked count unchanged |
| ROUTE | | the source's word count is the payload count when enabled, else 0; the destination as given |
| CLEAR | every engine in the mask halted | fault 0; still halted; execution state unchanged |
| EVENT | | each engine in the mask has a pending mailbox |
| FLUSH | the selected engine halted | its queues empty; every route whose source or destination is that engine has count 0 |
| TRIGGER | the selected engine halted; payload bits 23:6 zero | its trigger configuration is the payload's low six bits |

The checks go one way: an accepted command was legal and had the stated
effect. That a legal command is accepted is not specified here (an RTL that
rejected a legal COMMIT would pass). An accepted command is observed through
the processor's debug export. How the
eight host nibbles assemble the word, and that an invalid command is rejected
with the sticky host fault, is not part of this specification; the host-port
harness of [formal-depth.md](formal-depth.md) ("Host-port atomicity and read
snapshots") covers it. READ_SELECT changes only read-back state and has no
module.

## 3. How it is checked

### 3.1 Symbolic image

The engine index `k`, the image address `A` (0..63) and the word `W` are
`anyconst`: arbitrary, fixed for a trace. The harness assumes that a read of
address `A` of engine `k`'s instruction SRAM returns `W` on the next cycle
(the vendor model's registered read) and that address `A` is not written. A
single job therefore covers every engine, every address and every 32-bit
instruction word, including every operand and every invalid encoding.

### 3.2 The invariant V and why the one-step checks are unbounded

V is the set of states the checks start from:

- a fault stops its engine; a running engine has a committed image; a
  committed image has 1..64 words; an engine being loaded is halted and
  uncommitted;
- the blocked count is below LIMIT;
- a WAIT hold and an XFER are never in progress together;
- ownership is pairwise disjoint and open-drain lies inside ownership; queue
  levels are at most 8;
- for engine `k`: when it runs with `PC = A` inside its image, the SRAM output
  is `W`; and a non-zero blocked count at `A` means `W` is a well-formed
  WAITPIN or WAITEVENT.

Each one-step job assumes V in its first state only, and asserts V (plus
"program writes go only to a halted engine that is not starting") together
with its own properties on every step. `sby prove` (k-induction, depth 3)
proves the job. The base case covers every state of V; the induction step
shows that V and the properties are preserved from any state that satisfied
them for the previous steps. `isa_reset` shows that one reset edge from any
state lands in V. Together these show that V holds in every state reachable
from reset, and that each property holds on every edge out of such a state.

A program write to address `A` of engine `k` is excluded by assumption. This
does not weaken the result. Every one-step job asserts that a program write
happens only while its engine is halted and not starting; because `A` is
arbitrary, that assertion is checked for every write, in the instances whose
`A` differs from the written address. After a write to `A` engine `k` is
still halted (`isa_idle`), so the parts of V that mention `W` hold for the new
word, and the parts that do not mention `W` are shown preserved by the
instances with another `A`.

Clocked assertions report one step after the step they sample, so a check of
"state before an edge, state after it" needs depth 3. The first full run used
depth 2 and passed vacuously; the covers caught it (section 6, S0).

### 3.3 Bounded checks

The FIFO pointers are not observable, so an arbitrary starting state can hold
a queue whose level disagrees with its storage. `isa_queue_tx` and
`isa_queue_rx` therefore start on a FLUSH of engine `k`, which empties both of
its queues, and leave the host, the mover and all engines free from then on.
One word is tagged when it is pushed and followed through the queue. The TX
check needs a host or mover push, a START and the PULL after the FLUSH. Its
cover and its negative control first reach a PULL of the tagged word at step
19 (sby's numbering), so the check is vacuous below depth 20; the registered
depth is 21. At depth 21 (TX)
and 16 (RX) the checks cover a word pushed into an empty or nearly empty
queue; the order of several queued words is `fifo_conservation`'s unbounded
result for the queue itself. Deeper TX runs grow fast: depth 22 passed in
3,395 s (job 24411916, outside the registered job), and a depth-24 run was
stopped after 110 minutes without a result (job 24408557).

`isa_xfer_e2e*` follow one XFER from its issue edge to its final idle edge.
An XFER of `a` bits with half-period `b` makes `2a` transitions `b` cycles
apart, so it lasts `2ab` cycles after its issue edge. The three jobs bound
`a <= 2, b <= 2` (depth 12), `a <= 4, b = 1` (depth 12) and `a = 1, b <= 5`
(depth 14), which covers 8, 8 and 10 cycles after issue. Larger transfers are
checked by simulation only (section 8).

### 3.4 Covers and negative controls

Every check except `isa_inv` and `isa_reset` has a cover job. For an
instruction it shows an issue edge after which the instruction completes (PC
and count advance without a fault); HALT stops; FAULT and invalid words
fault; PULL and PUSH also block, PUSH a=1 overflows with fault 4, and WAITPIN
and WAITEVENT block and time out with fault 3. Command covers show each
command accepted for engine `k`. The witnesses start from a state of V, not
from reset: they show that the checks are not vacuous, not that the witness
state is reached from reset.

Every check except `isa_inv`, `isa_reset`, `isa_xfer_e2e_a4` and
`isa_xfer_e2e_b5` has a negative control: the same job on RTL with one seeded
defect, run as BMC from V without the V assertions. `formal/isa/mutate_isa.py`
generates the mutants from `processor_fv.v`. Each is a one-line edit (three
for `fetch_bound`, one per PC-bound compare) of engine 0's logic or of a
processor register that belongs to engine 0 (for SELECT, the selection
register). The edit is found structurally: engine 0's registers through the
`fv_*` concatenations, its opcode through the SRAM data pins, and the
multiplexer that the opcode, command, START or STOP selects. `run.sh` counts
a negative control only if one of the assertions that fired names the job in
a `target of:` comment.

## 6. Disagreements found

No RTL bug was found. Three literal readings of [isa.md](isa.md) disagreed with
the RTL where [isa.md](isa.md) did not decide the behaviour (isa.md has stated
all three since this specification was committed), and five
mistakes in the specification harness were found and fixed. Each entry names
the run and the values in its trace.

| # | Class | What | Evidence | Resolution |
|---|---|---|---|---|
| D1 | ambiguity in isa.md | HALT: "preserve queues and diagnostic registers" was read as PC and the completed-instruction count keep their values. The RTL completes HALT: at PC `0x3f` with count 1, HALT left PC `0x40` and count 2. [isa.md](isa.md) does not say whether HALT itself advances PC or is counted. | job 24402026, `isa_halt` (engine 2) | The specification follows the RTL. [isa.md](isa.md) could state that HALT completes (PC + 1, count + 1). |
| D2 | ambiguity in isa.md | START: "START resets PC, registers, local timers, repeat state and local logical outputs" does not list the completed-instruction count, so it was read as kept. The RTL clears it: count `0x80000000` became 0 on START. | job 24402026, `isa_cmd_start` (engine 3) | The specification follows the RTL. [isa.md](isa.md) could list the count. |
| D3 | ambiguity in isa.md | START does not list LIMIT or the PINS configuration either. The RTL restores LIMIT to its default (the register became `0xffff`, 65535) and clears PINS (engine 3: `0x100` became 0). | job 24402316, `isa_cmd_start` | The specification follows the RTL. [isa.md](isa.md) could list both. |
| S0 | specification bug | The first run checked at depth 2. Clocked assertions report one step after the step they sample, so no post-state was ever compared: every check passed and every cover failed. | job 24401535 | Depth 3 (section 3.2). |
| S1 | specification bug | V lacked "no WAIT hold during an XFER"; `isa_hold` failed from such a state, which is unreachable. | job 24402026, `isa_hold` | Added to V; `isa_inv` proves it. |
| S2 | specification bug | `isa_idle` required a halted engine's logical enables to stay unchanged; a BEGIN (which stops the engine) clears them. | S3 | specification bug | The queue tag counted a host RX pop at level 0 (`dbg_rx_pop` asserted on an empty queue; the queue ignores it). | job 24402026, `isa_queue` | Only a pop from a non-empty queue counts. |
| S4 | specification bug | From an arbitrary state the RX queue held a level that disagreed with its unobservable storage pointers: after a push into an "empty" queue the head was another word. | job 24402316, `isa_queue` | The queue checks start on a FLUSH of engine `k` (section 3.3). |

Two observations are representation, not disagreement: the LIMIT register
reads 0 after reset and `0xffff` after START, both meaning 65535; and BEGIN
and STOP clear a halted engine's logical enables, which are not visible at
the pins.

**Reproduction.** The disagreements D1 to D3 are reproduced by the literal
readings: in `formal/isa/isa_insn.sv`, give HALT `ISA_BLOCK` in place of
`ISA_COMPLETE` (PC and count unchanged); in `formal/isa/isa_cmd.sv`, assert
`cnt == $past(cnt)`, `limit == $past(limit)` or `pins == $past(pins)` after
START. Then `formal/run.sh isa_halt isa_cmd_start` fails with a counterexample
in `formal/build/sby/<job>/engine_0/trace*.vcd`.

## 7. Relation to the lockstep model

The cocotb suite runs the RTL and `test/model/reference.py` in cycle lockstep
([verification.md](verification.md)). Both were written by the same process
from the same contract, and the comparison is over simulated traces. This
specification differs in three ways:

- It is a third reading of [isa.md](isa.md), written without the Hardcaml
  source, the generated RTL's logic or the model (section 1 lists the earlier
  formal harnesses that were read).
- Its one-step properties are proved for every engine, image address,
  instruction word, register value and queue and mailbox state in V, on
  every edge of every reachable state, rather than on the traces a test
  reaches; PULL's loaded word, the RX append and the whole XFER schedule are
  bounded checks (section 3.3).
- It says only what [isa.md](isa.md) says, so it exposes the places where the
  implementations rely on decisions the contract does not record.

After the specification was frozen, the model was read at the points of D1 to
D3. Its `_start` clears `completed`, sets `limit = 65535` and clears `pins`,
and HALT (opcode 1) falls through to the common `pc = next_pc` and
`completed += 1`. The model therefore makes the same three decisions as the RTL.
That agreement is expected from the lockstep comparison, and it is the
common-mode case: both implementations share decisions that [isa.md](isa.md)
does not state.

What the lockstep suite checks and this specification does not: cycle timing
beyond one edge (except WAIT, XFER within the bounds above and the fetch
fault), the host nibble protocol and read-back, the mover, triggers, larger
XFERs, and whole programs. What this specification checks and simulation
cannot: every operand value and every encoding, including invalid ones, in
every reachable state.

## 8. What is not specified

- **Timing.** Pin timing and cycle budgets are covered by `pe_timing` and the
  timing certificates ([timing-certificates.md](timing-certificates.md)).
  Here, timing is specified only for one edge, the WAIT hold, the XFER
  schedule within the bounds of section 3.3 and the fetch fault.
- **Multi-engine interaction.** Non-interference between engines is the
  timing-isolation proof (`formal/README.md`, "Timing-isolation proof"). The
  checks here cover one engine at a time; because `k` is arbitrary, every
  engine is covered, and the checks allow any activity of the other engines
  and the host on the same edge.
- **The host port.** The nibble protocol, read-back (READ_SELECT), the sticky
  host fault and rejection of invalid commands are the host-port proofs of
  [formal-depth.md](formal-depth.md). Here a command is taken from the
  processor's accepted-command export.
- **Not observable here.** The stalled status bit, the XFER's internal
  counters and the final value of tx after an XFER (unspecified in
  [isa.md](isa.md)), the absence of a spurious mailbox delivery (deliveries
  from all sources are ORed into one observation), the mover's arbitration
  (`processor_invariants`) and the trigger detectors (`processor_inductive`).
- **Bounds.** Queue data is checked to depth 21 (TX; 22 once) and 16 (RX)
  after a FLUSH. XFER is checked end to end only up to the sizes of section 3.3;
  its issue edge (encoding, collision and ownership faults, idle level, first
  data bit) and its frame (`isa_hold`) are unbounded.
- **Design variants.** The jobs are registered for the design of record only.
  The area and reset variants and the line-unit extension
  ([isa.md](isa.md), "Configuration variants") are not specified here.
- **Implementation level.** These are RTL proofs of the generated Verilog with
  the vendor FUNCTIONAL SRAM models, like the rest of `formal/`. The
  observation ports are those of `processor_fv.v`, a debug variant of
  `src/protocol_emulator_core.v` (`formal/README.md`, "Limits").

formal/run.sh --list | grep '^isa_'   # 153 jobs and 5 groups
